# Research: bigger text in HD mode (for 0.5.x / 0.6.0)

Brief: the shared 0.5.0 research brief. Read-only on the repo. The prototype was built in a scratch copy, not in the repo.

## 1. What the game does today

### The port draws all text with the T2K engine, not with the bitmap fonts

The text-and-fonts spec (2026-10-13) describes the old hand port in `src/si/`. The shipped game is the full recompile, and it runs the original's own code with the original's default font mode.

- The font mode global 0x9cc2c4 is -2 in the exe and is set only at 0x5b1faf, from prefs+0x217, through the display init 0x5e2620 (calls at 0x5d79f7, 0x5d864f, 0x8aeedd). Nothing in `src/recomp_rt` or `tools/recomp` writes it.
- Measured in the running 0.5.0 build (lldb, HD, first text draw): 0x9cc2c4 = -2. The T2K draw 0x5b0d80 is hit from the line draw 0x5e5160 called by the text box 0x5e6d80.
- The original's Game Settings box has a "Fonts" row. Its values are "Futuristic" (mode -2, T2K, the default), "Traditional" (mode -1, the seven `.fnt` bitmap fonts) and any `.ttf`, `.ttc` or `.t2k` file in `Data/FONTS` (mode 0 and up, scanned by 0x5b2170). Strings near 0x9cc2c8.
- The T2K files are in the clean files: `Data/small.t2k`, `medium.t2k`, `large.t2k`, `symbol.ttf`. The loader 0x5b0b60 loads them into 0xaebdf4 (symbol.ttf), 0xaebdf8 (small), 0xaebdfc (medium), 0xaebe00 (large), called at 0x5e4a71..0x5e4ab3.

### T2K sizes are constants in the code

| Font number | T2K font | Size (px) | Baseline offset | Line height |
|---|---|---|---|---|
| 0 | symbol | 9 | +3 | 15 |
| 1 | small | 9 | +3 | 15 |
| 2 | small | 10 | +4 | 18 |
| 3 | medium | 14 | +4 | 21 |
| 4 | medium | 16 | +4 | 24 |
| 5 | medium | 18 | +4 | 27 |
| 6 | large, bold | 20 | +9 | 39 |
| 7 | large, bold | 22 | +11 | 45 |

The constants are in seven places, 59 instructions in all (list in `docs/research/2026-10-16-hd-text-patches.txt`):
- the line draw 0x5e5160: sizes and baselines at 0x5e52ce..0x5e53f6 (pushed to 0x5b0d80), cursor heights at 0x5e5454..0x5e54d2 and 0x5e59cb..0x5e59f5;
- the text width 0x5e5ad0: sizes at 0x5e5b1f..0x5e5bea (pushed to 0x5b18a0);
- the text height 0x5e5cd0: 0x5e5cea..0x5e5d0e;
- the text box 0x5e6d80: line heights at 0x5e711f..0x5e7149 and 0x5e7618..0x5e7642.

The other 30 reads of 0x9cc2c4 (0x5ede39, 0x719463, 0x75dd2c and others) only choose a symbol character (arrows) for T2K or bitmap. They hold no sizes.

### How the picture reaches the screen

- The game draws into one RGB565 frame: 1280x800 in widescreen, 1920x1080 in HD (`display.c` win_read_settings). Area and widget rects are scaled from 800x600 (`display.c` scale). Text is not scaled.
- The frame goes to an SDL texture. `SDL_RenderSetLogicalSize` fits it to the window with bars (`user32.c` win_video_init). The window has `SDL_WINDOW_ALLOW_HIGHDPI`, so on a Retina Mac the output is in physical pixels.
- `sharp_picture` (default on): nearest filter, and whole-pixel scale when that keeps 80 % of the fit (`user32.c` update_scaling, WHOLE_PIXEL_SHARE 0.8).
- Text width for layout: the wrap of 0x5e5ad0 in `display.c` gives screen code the width in classic pixels (width x 800 / screen width). Bigger text therefore gets wider layout boxes on its own.

### Real text size (font 1, size 9 px, the list and note text)

| Screen | Widescreen scale | Widescreen text | HD scale | HD text | HD / widescreen |
|---|---|---|---|---|---|
| Retina window 1800 physical px wide | 1.41 | 12.7 px | 0.94 | 8.4 px | 0.67 |
| 1080p, full screen | 1.35 | 12.2 px | 1.00 | 9.0 px | 0.74 |
| 4K, full screen (native) | 2.70 | 24.3 px | 2.00 | 18.0 px | 0.74 |

On the 1800 px Retina window, HD is scaled down (0.94). With sharp_picture the nearest filter drops about 1 row and column in 16, so thin strokes of 9 px text can vanish. This is a second cause of "very small" on Max's MacBook. [inference: from the scale factor; not checked on Max's screen]

Proportion to widgets: HD widgets are 1.5x wider (1920/1280) and 1.35x taller (1080/800) than widescreen widgets, but text is 1.0x.

## 3. Ways to make HD text bigger

### (a) Scale each glyph by 1.5 when drawn

Not needed. The glyphs come from T2K, a vector font engine that draws at any pixel size. Scaling its output would be worse than asking T2K for the bigger size. A glyph scale would only matter for the "Traditional" bitmap fonts.

### (b) Bigger T2K sizes in HD (prototype built)

Turn the 59 constants into a run-time value with the existing mechanism of `tools/recomp/widescreen.py` (PATCHES: address, constant, C expression). Prototype in `hdtext/proto/src` (scratch copy of HEAD, build `hdtext/proto/build/cm0102_recomp`, 74 s build):
- `tools/recomp/hd_text.py`: 59 entries `addr: (v, 'rt_hd_text(v)')`, merged into PATCHES;
- `rt.h` and `display.c`: `rt_hd_text(v)` returns v outside HD and round(v x k) in HD; k from `HDTEXT_SCALE` (default 1.5).

Results (pictures in a scratch folder, not in the repo):
- k = 1.5: text matches widescreen in width share. The squad screen, Bosman Edition Options, manager menu, Game Settings and profile read well (shots 3, 7, 8, 10, 11). The side bar and the popup items grow with the text.
- Lists use the text height for their rows. The squad list shows 8 rows a column at 1.5 and 9 at 1.35, against 10 in widescreen and 10 with spare space in HD today (shots 1 to 4). A scroll bar appears.
- Overflow and cuts seen at 1.5: the note "Applies at the next start" of Display mode is cut at the right edge of the Options box (shot 8, `options_screen.c` counts 8 px a character in HD, line 223); on the profile, "Work Rate" touches the stats bar below (shot 9; `groups.c` uses rows of 17 px, line 129). Not swept: every other screen.
- Drop-down items are taller, so every HD click position on a popup item changes. The tests with HD positions need new ones (`smoke_run.py` Go on Holiday "| 270 541" became 303 651; `options_box_run.py` OPTIONS_ITEM; `attribute_groups_run.py`; `smoke-ref/hd` pictures).
- Runtime code with its own text metrics to check: `options_screen.c` (notes), `groups.c` (profile rows), `squad_depth.c` (rows of 3 text heights), `compare.c`, `best_xi.c`, `views.c`, `columns.c`. `names.c` measures with the game's own 0x5e5ad0, so it follows.
- The "Traditional" font (mode -1) is not scaled by this. A player who picks it in HD keeps small text.

Cost: one slice. About 60 lines in `tools/recomp`, a few in the runtime, fixes in about 5 runtime screens, new HD test positions and HD reference pictures. Risk: two-way door, HD only (outside HD `rt_hd_text` returns the old value, and the prototype at k = 1.0 gives a save byte for byte equal to the 0.5.0 build).

### (c) A smaller HD frame or an integer scale

- 1600x900 or 1600x1000: text is 1280/1600 = 0.8 of widescreen and the extra space over widescreen drops from 2.0x to 1.4x of the pixels. Half a fix at the cost of HD's purpose.
- Integer scale: sharp_picture already uses it when it keeps 80 % of the fit. On a 1080p or 4K screen HD is already 1x or 2x. It does not make text bigger.
- A fix for the Retina downscale: in a window smaller than 1920x1080 physical, use the linear filter even with sharp_picture. Cheap (`user32.c` update_scaling), no game change. It removes the lost strokes, not the small size.

### (d) Other ways

- Map font numbers to bigger ones in HD (font 1 to font 3, and so on): the typeface changes (small.t2k to medium.t2k) and only 8 steps exist. Worse than (b).
- The original's bitmap fonts: fixed sizes (arial 14/16/18, arial narrow 10/11, trade condensed 24/28). Nothing larger exists.
- Draw the whole HD frame at 1280x800 and scale up: that is widescreen.

## 4. Can it change game decisions?

Yes, like a display mode. Same-save check from `start.sav`, HD, 14 game days (scratch scripts):
- prototype k = 1.0 against the 0.5.0 build: same save;
- k = 1.5 against k = 1.0: every part of the save differs (player.dat, fixtures, news and the rest);
- k = 1.5 against k = 1.5 again: same save, so the game repeats.

The clicks were the same except the Go on Holiday item, which moved. [inference: the cause is the memory layout: T2K allocates its glyph work memory by size (0x5b1a00 calls the engine at 0x93fa90..0x93de70), and lists build a different number of rows.] Under Q152 this is the same kind of difference as classic, widescreen and HD. An in-game switch would break the rule. A setting that applies at the next start, as the display mode does, does not.

Test plan: same-save check with the HD text on, run twice (repeatable); the k = 1.0 build against the release build (no change outside HD, and in HD with the scale at 1); smoke run in HD with new positions and pictures; widescreen and classic smoke runs unchanged.

## 5. Open decisions for Max (recommended answers)

1. **Approach.** Recommended: (b), bigger T2K sizes in HD through the PATCHES table. Reason: the engine already draws at any size, the prototype works, and the cost is one slice.
2. **Factor.** Recommended: 1.35 (sizes 9, 10, 14, 16, 18, 20, 22 become 12, 14, 19, 22, 24, 27, 30). Reason: 1.35 is the height ratio of HD to widescreen, so lists keep about as many rows as widescreen, and text is 90 % of widescreen's width share, so it overflows less than at 1.5. 1.5 matches widescreen width but loses two list rows.
3. **Option or fixed.** Recommended: a setting `hd_text = large | small`, default large, applied at the next start like the display mode, on the Screen tab next to Display mode. Reason: it changes the game like a display mode (Q152), and some 4K players may want the small text for more rows.
4. **Widescreen too.** Recommended: no. Reason: widescreen is the default, nobody asked, and it would change every default game and all widescreen reference pictures.
5. **Retina downscale.** Recommended: yes, use the linear filter when the HD frame is scaled below 1x, in the same release. Reason: cheap, no game change, it fixes lost strokes on MacBook windows.
6. **Release.** Recommended: 0.5.1, one slice, before the 0.6.0 build. Reason: small and HD only. 0.6.0 is a large season release.
7. **"Traditional" font in HD.** Recommended: leave it small and say so in the option note. Reason: no player asked for the bitmap fonts.
